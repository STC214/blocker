# AdClose 完整使用流程

核对日期：2026-10-17。依据本地 AdClose 提交
`11f9e5547ec1e89ad7daf7114d05a0b02aa96de1`（源码 versionName 4.3.7）。
这是使用指南；本次没有修改、构建、安装或推送 AdClose 仓库。

## 1. 先理解分工

| 工具 | 工作层级 | 前提 |
| --- | --- | --- |
| 本分支 Blocker | 系统 IFW / 组件状态 | IFW 操作需要 root |
| AdClose | 应用进程中的 SDK 初始化方法、网络请求 Hook | 已工作的兼容 Xposed 框架、模块激活和目标应用作用域 |

有 root 不等于 AdClose 已生效。Blocker 的 IFW XML 不是 AdClose 的 Hook 配置，两者不直接互相导入。
广告 SDK 的普通类名也不一定是 Android 的 Activity/Service/Receiver 组件名。

## 2. 确认框架条件

1. 先备份重要数据和当前 Blocker/AdClose 配置，保存现有正常工作的模块版本。
2. 打开现有 LSPosed/兼容框架管理器，确认框架正在运行，而不只是装了管理器 APK。
3. 本地 AdClose 的 `META-INF/xposed/module.prop` 指定 **minApiVersion=101**。
   所选框架须支持对应现代 libxposed API；旧 API 100 构建不满足此源码声明。
4. 若框架已经满足要求，不要为了本指南重新安装另一套框架。
5. 若缺框架：通过所选框架作者的官方仓库下载与系统匹配的模块，在 root 管理器中安装，
   配齐其要求的 Zygisk 环境，重启，再从框架通知/管理入口确认运行状态。
   不要同时启用两套同类框架或两套 Zygisk 实现。

此前手机识别为 Android 17 + KernelSU，但本轮 ADB 没有连接设备，未验证当前框架状态。
[Vector 官方说明](https://github.com/JingMatrix/Vector)目前列出 Android 8.1–17 Beta、
Magisk/KernelSU + Zygisk 条件；这不是对所有 Android 17 正式版 ROM 的兼容保证。
应核对具体发行说明和 API 支持，再决定安装包，而不是只比较版本号大小。

## 3. 安装与激活 AdClose

1. 从 [AdClose 作者发行页](https://github.com/zjyzip/AdClose/releases)获取 APK，区分正式版与预发布。
   发布版的界面可能与本地分支不同。克隆源码本身不会生成可安装应用。
2. 安装 APK，进入框架的“模块”页，开启 AdClose。
3. 作用域先只勾选 **一个待测试的普通应用**。不要全选系统框架、System UI、桌面、银行或支付应用。
4. 打开 AdClose，确认 Home 中激活/服务连接状态正常。
5. 如果提示未激活，先处理框架版本、API 101、模块开关和服务连接，不要靠不停添加规则排障。

若原来装过另一签名的同包名 APK，覆盖安装会出现签名不一致。先导出配置再选择保留原版或迁移，
不要把卸载当作默认修复。本地源码的签名配置也不代表你持有作者的发行密钥。

## 4. 第一轮：只开 SDK 广告拦截

1. AdClose → **Apps → 用户应用**，搜索目标应用并进入其配置。
2. 打开 **阻止SDK广告初始化**；按界面保存开关配置。
3. 排障时可暂时开 **启用Hook提示**，帮助确认目标进程被注入。
4. 暂不打开 Native 请求、环境检测、剪贴板等附加功能，保持变量最少。
5. 在 Android 应用信息中“强行停止”目标应用，再重新打开。
   仅从最近任务划走不一定终止后台进程。调整规则后都按此方式冷启动测试。
6. 进入原来出现广告的页面，重复原来的触发动作。
7. 同时测试启动、登录、播放、搜索、下载、通知等主要功能；“广告少了”不等于没有误伤。

## 5. 第二轮：自动检测广告 SDK

仅在第一轮仍有广告时进行：

1. 进入目标应用的 **自定义 Hook / Hook 配置**页面，确认该应用 Hook 总开关启用。
2. 在操作菜单中选择 **自动检测广告SDK**。本地源码会尝试启动目标应用；随后返回 AdClose 查看结果。
3. 此分支有管理器侧扫描回退：等候约 5 秒后开始回退，不是保证 5 秒扫描完成。
   APK 大小、设备性能和动态加载代码都会影响结果。
4. 在“检测到以下广告初始化方法”对话框中检查候选，分批选择后点“导入”。
   对话框默认勾选候选不代表每项都适合屏蔽；统计、崩溃上报或混合用途 SDK 可能被一起识别。
5. 检查导入项及总开关，保存后强行停止并重开目标应用，再测试。
6. 没有新候选可能表示已导入、规则未覆盖、混淆或代码动态加载，不代表应用没有广告。

## 6. 第三轮：网络请求拦截

1. 打开该应用的 **应用请求检查**，保存并冷启动。
2. 在目标应用中复现广告，再回到 AdClose 的 **Request / 请求列表**。
3. 根据触发时间和请求内容，识别与广告相关的请求；将确认项加入拦截列表。
4. 优先窄范围规则，不要直接屏蔽整个业务域名或通用 CDN；同一域名可能同时承载登录、内容和广告。
5. 冷启动并重测。误伤时删除新规则或加入放行列表；一次只调整一类规则。
6. **应用 Native 请求检查**最后才考虑。项目自身标注其稳定性较弱，开启后要单独验证。
7. 请求记录可能包含账号标识、URL 参数和正文，分享日志前先移除敏感字段。

## 7. 与当前 Blocker 配合

1. 保留已验证有效的 Blocker 规则并先导出备份，不要为安装 AdClose 清空 IFW。
2. 首轮只改变 AdClose 设置，观察它对现有 Blocker 配置的增量效果。
3. SDK 方法级广告交给 AdClose；明确的广告组件才由 Blocker 针对性处理。
4. 避免同一轮同时改两边；发现故障，优先撤回最近一边的改动。
5. 若需要判断故障来源，分别测试：现有配置、关闭该应用 AdClose 作用域后冷启动、
   恢复该应用最近的 Blocker 改动后冷启动。不要全局解封所有应用。
6. 本分支 IFW 每次写入/删除结束都会设目录为不可变；AdClose 不负责该目录的解锁和恢复。

## 8. 验收、备份与故障恢复

建议每个应用保留记录：应用版本、AdClose/框架版本、启用开关、导入规则、广告触发路径、
主要功能测试结果。稳定后导出配置，关闭临时提示和不需要的请求采集。

| 现象 | 优先检查 |
| --- | --- |
| AdClose 未激活 | 框架运行状态、现代 API 101 支持、模块开关、服务连接 |
| 显示激活但没效果 | 目标应用作用域、应用内开关、是否冷启动、广告是否属于支持范围 |
| 自动扫描没有结果 | 目标启动及返回结果、总开关、等待回退、候选是否已导入 |
| 请求列表为空 | 请求检查开关、目标冷启动、是否真正触发请求、是否走 Native/未覆盖网络库 |
| 闪退或登录失败 | 先撤回最近规则，关闭 Native 请求检查；仍异常则取消该应用作用域后冷启动 |
| 取消作用域仍异常 | 检查独立存在的 Blocker IFW/PM 规则；停用 AdClose 不会恢复它们 |

目标应用严重异常时，先在框架管理器移除它的 AdClose 作用域并强行停止后重开。
若是框架安装后整机异常，按 root 管理器/框架官方恢复步骤停用新模块；不要反复叠加安装。

## 源码依据

- [本地分支固定提交](https://github.com/STC214/AdClose/tree/11f9e5547ec1e89ad7daf7114d05a0b02aa96de1)
- `app/src/main/resources/META-INF/xposed/module.prop`：现代 API 101。
- `app/src/main/res/values-zh-rCN/strings.xml`：上述中文按钮名称。
- `HookLogic.kt`、`SettingsManager.kt`：功能开关与 Hook 分工。
- `CustomHookManagerFragment.kt`：扫描候选和选择性导入。
- `CustomHookViewModel.kt`：5 秒后启动管理器侧扫描回退。

本指南未将 AdClose 代码合并进 Blocker；两项目的许可证和功能边界保持独立。
